# Первичная подготовка временной сетки CAD-просмотра

## Что исследовано и изменено

Подготовка временной сетки для вращения, а не построение CAD и не полный кадр. Профилирование синтетических сцен показало заметную долю времени в вычислении границ групп. Для каждой группы минимум координат вычислялся отдельно, а затем `np.ptp` повторно вычислял тот же минимум вместе с максимумом. Теперь для вычисления размера группы используется уже найденный минимум. Остальной алгоритм — группировка, порядок, пороги, шаг сетки, удаление вырожденных и совпадающих треугольников и отбор для очень крупных сеток — не менялся. Расчёт остаётся в GUI-потоке, CAD-геометрия и сохранённый документ не меняются.

Это общий алгоритм визуальных групп; он не предполагает две трубы. Он по-прежнему создаёт приближённую сетку только для движения и не даёт гарантий точности CAD или инженерной пригодности.

## Сопоставление с исходной реализацией

Linux, Python 3.11.2, NumPy 2.4.6, синтетические маленькие случайные треугольники с фиксированным seed. Для каждого сценария проверено точное совпадение выходных массивов, затем после прогрева исходный и новый варианты выполнялись в чередующемся порядке по 10 раз. В таблице — медианы и диапазон каждого из них, миллисекунды. Измеряется только упрощение по целым группам; здесь нет CAD-построения, первого кадра, клика или GPU. Данные: `cad_interaction_paired.json`.

| Треугольники / группы | До, медиана (мин–макс) | После, медиана (мин–макс) |
| --- | ---: | ---: |
| 50 000 / 1 | 38,88 (38,02–54,69) | 36,49 (33,68–43,31) |
| 50 000 / 100 | 56,53 (52,03–65,55) | 49,51 (47,47–58,51) |
| 200 000 / 1 | 170,37 (158,28–199,05) | 152,09 (143,12–157,74) |
| 200 000 / 100 | 177,98 (162,32–192,63) | 148,65 (141,56–238,69) |
| 200 001 / 100 | 92,01 (90,17–108,54) | 87,01 (83,71–95,58) |

Разброс значителен и диапазоны местами пересекаются: нельзя утверждать универсальное ускорение. Разница между 200 000 и 200 001 связана с **уже существующим** порогом более грубой временной выборки при числе треугольников выше 200 000, а не с этим изменением. Размер и состав временной сетки до/после совпадают в каждом сценарии.

В отдельном последовательном замере полного вызова подготовки виджета `set_mesh` для сцены 200 000 / 100 получено 294,35 → 265,49 мс; измерение включает и другие шаги, в том числе границы и оттенки. Пять повторов и другие сценарии, включая частичную маску, — `cad_interaction_before.json`, `cad_interaction_after.json`. Эти замеры не попарные и могут зависеть от нагрузки. Потребление и пиковая память не измерялись.

Воспроизведение из корня репозитория с установленными зависимостями; файл исходного модуля должен быть доверенным, так как диагностический скрипт исполняет его как Python-код:

```sh
git show 45578b7822028cfa4b9e676ac1a0ca330ec73796:suspensionlab/suspensionlab/core/cad_interaction.py > /tmp/cad_interaction_reference.py
cd suspensionlab
python diagnostics/cad_interaction_compare.py /tmp/cad_interaction_reference.py
QT_QPA_PLATFORM=offscreen python diagnostics/cad_interaction_timing.py
```

В среде замеров дополнительно использовались временные системные библиотеки Qt через `LD_LIBRARY_PATH`. Это не тест целевой Windows-машины. Синтетическая сцена не является проектом каркаса.

## Отдельный диагностический срез запуска CAD-процесса

В том же Linux-окружении отдельно запущены свежие процессы Python с чередованием порядка сценариев, по 10 повторов. Измеряется полное время запуска, указанных импортов **и завершения** процесса: пустой Python — медиана 48,66 мс (32,25–64,96); с `numpy` — 139,92 мс (114,31–168,94); с модулем рабочего процесса сварного рычага — 165,08 мс (164,79–265,34); с этим модулем и импортом `OCP.BRepCheck` — 1370,14 мс (1221,87–1573,06). Исходные данные и версии — `cad_worker_startup_timing.json`, команда `python diagnostics/cad_worker_startup_timing.py` с нужными системными библиотеками в окружении.

Это указывает, что запуск с CAD-зависимостью заслуживает изучения в этом стенде. **Это не замер реального CAD-задания:** отсутствуют чтение модели, построение, проверки, передача сетки и отмена; время завершения включено, а порядок импортов и условия отличаются от реального рабочего процесса. Нельзя вычитать эти величины из ранее измеренного задания или переносить их на Windows. Изоляцию и отмену процесса не убирали.

## Проверки и оставшаяся работа

Независимый тест прежней реализации сравнивает массивы в точности для 12 000, 12 001, 50 000, 200 000 и 200 001 треугольников, одной и 100 групп, полной и частичной подсветки, совпадающих/перевёрнутых, вырожденных и негруппированных треугольников. Кэш целых групп и переход к частичной маске проверены отдельно.

Локально Linux/offscreen: профильная регрессия рендерера и редактора **122 passed, 1 skipped** (реальный GL), отдельный прогон при масштабе 150% **23 passed**. Ruff и mypy прошли. Полный тестовый набор, реальный GPU, Windows и собранная программа не проверялись.

Подготовка по-прежнему может блокировать GUI на больших сетках. После этого прохода выполнено раздельное инструментированное измерение изолированного задания, включая передачу и чтение результата; методика, новые данные и ограничения — `cad_job_transport_investigation.md`. Для решения дальнейших блокировок нужно проверить отмену, владение данными и устаревание результата прежде, чем переносить вычисления с GUI-потока. Работа над полноценным рабочим полем и независимым стартом по трём точкам ещё не завершена.
